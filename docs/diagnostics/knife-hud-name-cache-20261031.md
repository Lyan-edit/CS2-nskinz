# 刀具右侧 UI 名称与实际涂装不同步（2026-10-31）

## 现象

刀具的模型或实际材质已经切换成功，但右侧武器栏仍显示上一次刀具的本地化名称，例如实际画面已不是虎牙，UI 仍显示“爪子刀（★）| 虎牙”。该问题同时可能出现在：

- “仅饰面”：原 Demo 播放期间的材质热修；
- “模型+饰面”：临时 Demo 重建后再次加载同一刀型、不同涂装。

右侧武器栏使用经济物品身份缓存本地化刀名和涂装名；材质字段正确并不代表这个名称缓存已经失效。2026-11-03 的复现还涉及更新后材质同步 ABI 校验失败，导致名称刷新一直等待；见下方对应日期记录。

## 根因

0.6.6 的临时 Demo 刀具身份由“玩家 XUID + 刀型”生成，没有把 `paint_kit` 纳入身份。同一玩家保持刀型不变、只更换涂装时，重建后的 `m_iItemIDHigh:m_iItemIDLow` 与上一份临时 Demo 相同。CS2 因而可复用旧的 UI 名称缓存，但渲染仍读取新涂装属性，于是出现“实际材质已变、UI 名称未变”。

实时“仅饰面”链还会保留来源刀具的真实库存高位 ID。即使动态属性与 fallback 涂装已经更新，右侧 UI 仍可能从原库存身份取得旧名称。原快速路径只核对涂装属性和材质数量，没有把用于 UI 的完整经济物品身份、`m_bDisallowSOC`、初始化状态与名称字段纳入稳定状态验证，错误缓存因此可能被当作已完成状态跳过。

2026-11-01 的复现日志还确认了一个更直接的条件分流错误：写入端只在“模型+饰面”时生成涂装专属的 `m_iItemIDHigh`，“仅饰面”仍写入 `0xFFFFFFFF`；但验证端对任何显式刀具涂装都要求涂装专属身份。所以仅饰面的精确管线会必然验证失败、回滚，再降级到不能刷新 HUD 名称的 world-carrier 字段写入。现在写入与验证统一使用同一个“是否存在显式涂装意图”判定，不再用是否换刀型决定 UI 身份。

## 修复

### 模型+饰面：仍然只走临时 Demo

- 临时 Demo 重建器现在用“玩家 XUID + 目标刀型 + 目标 `paint_kit`”生成独立的刀具经济物品身份；刀型相同但涂装变化时，高低位 ID 都会变化。
- `player_death` 中的 `weapon_itemid` 使用与刀实体相同的新身份；`weapon_fauxitemid` 继续编码目标刀型和涂装。因此右上角击杀信息与右侧武器栏不会使用两套互相矛盾的身份。
- 没有把模型、动画、Subclass 或材质替换重新接入实时模型链。模型+饰面的模型和涂装来源仍完全是临时 Demo 重建。

### 仅饰面：仍然只走 Demo 内热修

- 显式刀具涂装不再保留来源库存高位 ID，而是生成带命名空间、随“玩家 + 当前刀型 + 涂装”变化的客户端身份；同时继续写入新的材质缓存低位 ID并设置 `m_bDisallowSOC`。
- 稳定快速路径现在验证完整经济物品状态，而不只验证三个涂装属性。身份、SOC 脱离、初始化、账户、质量、fallback 或名称字段任何一项被 Demo 复制回旧值，都会重新进入一次有界修复；材质完成且所有字段稳定后仍走原有低开销快速路径。
- 仅饰面路径不会写刀型定义、模型、动画图或 Subclass。

## 回归门禁

- C++：验证相同玩家和刀型在 `paint_kit` 改变时 UI 身份必然变化，并确认新身份不等于来源真实库存 ID。
- Rust：验证临时 Demo 刀具身份随涂装变化且保持在 nSkinz 客户端命名空间；刀实体与击杀事件使用相同身份。
- 路由：`FinishOnly` 仍只进入实时饰面管线；`ModelAndFinish` 仍只由 `BuildDefaultDemoSkinRewritePlan` 写入临时 Demo，不允许退回实时模型替换。

## 2026-11-02：仅饰面材质未更新

用户复现日志明确停在 `native knife material-copy evidence is not verified for this client`。已安装客户端为 2000939，但 `KnifeFinish.hpp` 仍使用 2000935 的固定函数地址与调用字节窗口。世界刀实体刷新后，HUD 材质复制被校验拒绝，因此画面中的刀仍使用旧饰面。这与 UI 名称身份问题是两个独立故障。

当前 `client.dll` SHA-256：`D618BBF8E6AFB36BAA09B3A282035996A88300458C55D2AA5CB81F0495C0EC54`。

核对安装二进制的原生调用与虚表后，更新复制 `0x14EBCB0`、应用 `0x95BB60`、通知 `0x956320`、清理 `0x14EBB70`，以及当前模型读取、生成失败清理和原生 HUD 构造的调用证据。通知函数对模型持有者的偏移已由 `-0x2D0` 变为 `-0x2D8`，原皮清理路径的签名也同步更新。保留完整字节、模块范围、世界/HUD 所属关系和同刀型校验。

新增独立的安装二进制验证入口：设置 `NSKINZCS2_KNIFE_FINISH_CLIENT_DLL` 后运行测试，可验证仅饰面 ABI，无须启用实时换刀型的动画／模型证据组。测试逐字节破坏和截断窗口，要求全部拒绝；本次使用上述真实客户端通过验证。

## 游戏内验收

### 2026-11-02：补齐名称缓存本身的失效

仅更新高低位 ID、SOC 标志和涂装属性不足以刷新已生成的名称。本次直接核对了安装客户端的 `C_EconItemView::GetItemName`：`+0x1192620` 检查 item view 的 `+0x200` 名称描述指针；指针非空时跳过生成并返回旧缓存，根本不会重新比较涂装或物品 ID。原生 Econ 属性 setter 在修改属性后会调用 `+0x11A0A20`，析构该描述及其缓冲区，并把指针清空；现有原地写入管线缺少这一步。

右侧武器栏的实际调用点为 `client.dll+0xEAAD98`：取得同一 getter 的返回值后，在 `+0xEAADBC` 交给 `WeaponIcon--name` 更新接口。这处调用也加入字节验证，名称控制器处理的是实际 HUD 消费者使用的缓存。

独立的 64 位 `m_iItemID` 也存在，但所核对的名称消费者会拼接 `m_iItemIDHigh/Low` 匹配物品。不能据此认定必须直接改写缓存的 64 位 ID；本次修复不修改该字段或物品注册表元数据。

修复新增 UI 名称控制器。在当前玩家的活动刀具完整句柄、owner、物品载体和实体代次都验证通过，且实际 definition／fallback paint／Econ paint 与请求一致后，调用原生失效函数，再调用原生名称 getter 生成并回读新名称。日志 `Knife HUD native name regenerated` 会记录 definition、paint、物品身份，以及 `before`、`after` 两份实际名称，不再把“涂装字段一致”当成名称成功的证据。

- 仅饰面：饰面热修后刷新名称；即使材质走稳定快速路径，名称控制器仍会执行。
- 模型+饰面：只在生成的临时 Demo 中，且序列化刀型与涂装已经符合配置时刷新名称缓存。该控制器不写模型、涂装、质量、ID 或属性列表；模型和涂装仍完全来自 Demo 重建。
- 每个物品／配置／实体代次只尝试一次，失败也停止重试，直至 Update、seek 或实体重建。稳定播放不重复生成名称或材质。来源字段被复制回来后重新修复，会重新安排一次名称失效。
- 当前客户端的 getter、缓存释放、原生 setter 和名称消费者均加入安装二进制字节验证，并测试逐字节改变、截断时必须拒绝。

### 仅饰面：名称提交必须等待同一配置的材质完成

2026-11-02 22:58:59 的实际日志表明名称缓存已失效，但 `world-to-HUD material transfer verified` 到 22:59:04 才出现。此前名称控制器只核对了字段，可能在材质异步生成期间提前发布新名称。

现在仅饰面名称控制器还必须同时确认：世界武器刷新签名、当前 HUD 武器刷新签名，以及成功复制到 HUD 的材质签名，都等于本次配置的精确签名。上一份涂装已完成、只有世界材质完成、HUD 尚未绑定等情况均等待。名称控制器仍在材质快速路径之外执行，因此不会被“材质已完成”分支跳过。

本次日志的中文 `before` 字段还触发了现有宽字符日志流的编码失败，整行在该字段处截断。名称诊断改用 ASCII JSON 转义记录本地化文字，保留原始 Unicode 内容及完整 `after` 字段；没有把日志截断误判为名称 getter 未执行。新增回归覆盖新旧材质签名、世界／HUD 独立完成状态，以及中文、星号、引号和换行的日志保留。

本次环境没有运行中的 CS2，原生调用证据和离线回归不等于 HUD 已在画面中验收。游戏内验收需同时检查日志的 `after` 名称和右侧 HUD 标签；若两者不同，剩余问题在标签更新层，应继续核查，不能再次只修改涂装属性。

1. 完全退出仍加载旧 DLL 的 CS2/HLAE 进程，再加载新构建。
2. 仅饰面：保持同一刀型，连续选择两个名称不同的涂装；确认实际材质、右侧刀名/涂装名同步变化，切枪、seek、暂停恢复后仍一致。
3. 模型+饰面：从原 Demo 分别生成两份“同刀型、不同涂装”的临时 Demo；每次用生成按钮重新加载，确认右侧 UI 名称与画面一致。
4. 用刀击杀时同时确认右上角击杀图标、事件刀型与右侧武器栏一致。

离线字段回读、构建和自动测试不能代替 Panorama 的实际画面验收；如果游戏内仍显示旧名称，需保留新 DLL 的 `nSkinzCS2.log`、`nSkinzCS2.ui.log` 和对应生成 Demo，继续检查当前版本新增的 UI 消费者缓存。

### 2026-11-03：2000940 更新阻断材质同步与名称刷新

实际测试日志从 20:36:59 开始，游戏为 `ClientVersion=2000940`、`PatchVersion=1.41.9.5`、`SourceRevision=11198439`。20:37:11 和 20:37:22 均出现 `native knife material-copy evidence is not verified for this client`，随后名称控制器记录等待当前材质复制。该轮没有执行名称失效或名称 getter，不能把它判为“原生新名称已生成但 Panorama 没显示”。

本机 `client.dll` SHA-256 为 `57ee728e15c50881070d847d7516d632d70456e0648d486a53f2528ec53f6ee0`。对其 PE 指令及原生调用关系核对后，更新以下地址：

| 用途 | 2000940 RVA |
| --- | --- |
| 原生材质复制 | `0x14EBCC0` |
| 材质 apply／changed／clear | `0x95BB70`／`0x956330`／`0x14EBB80` |
| 原生 HUD 创建时复制材质的调用点 | `0x10D8839` |
| 生成失败时清理材质的调用点 | `0x804210` |
| 名称 getter／缓存释放 | `0x1192630`／`0x11A0A30` |
| 原生 Econ setter 释放名称缓存的调用点 | `0x1192E52` |
| 右侧 HUD 调用名称 getter 的调用点 | `0xEAADA8` |

这些入口相对 2000939 移动了 `0x10`，但材质 apply 调用的当前模型 getter 仍是 `0x21C8D0`，对应 `rel32` 从 `0xFF8C0D49` 变为 `0xFF8C0D39`。不能整体加偏移后继续接受旧调用字节，也不能取消校验。

修复同时更新材质和名称两组指令窗口，补充材质 clear 入口校验。安装二进制回归额外从真实 PE 解码五条直接调用，分别检查模型 getter、材质 clear／copy、名称释放／getter 的实际目标；保留逐字节破坏及截断拒绝测试。更新前的测试明确在安装材质 ABI 上失败。

材质和名称的配置签名及实体代次检查继续生效；仅饰面仍完全走 Demo 内热修，模型+饰面仍从临时 Demo 获取模型与涂装。未来校验不匹配时，日志明确记录“材质及 HUD 名称同步被阻断”和已核验的客户端版本。

交付时只做本机二进制校验、自动回归与 DLL 编译，不启动 HLAE。当前版本的右侧 HUD 画面仍需用户加载新构建验收；不能用离线测试代替该步骤。

### 2026-11-03：名称描述刷新后仍未更新已存在的 HUD 图标

20:54:56 的新日志证实，2000940 的材质复制已经通过，名称失效函数也已执行。但是原诊断的 `before` 和 `after` 都是 `''nSkinz CS2''`：这是调用 `GetItemName(false)` 得到的自定义名，不能证明“蝴蝶刀 | 蓝钢”已经变成“蝴蝶刀 | 多普勒”。用户截图中实际刀面与观战信息已经变化，右侧仍显示蓝钢，与这处诊断遗漏一致。

进一步核对当前客户端和安装 VPK 中的 `hudweaponselection.vxml_c` 后，确认右侧文字由武器图标的 `WeaponIcon--name` dialog variable 驱动。`client+0xEDA090` 按 `view+0x50` 的数量遍历 `view+0x58` 的图标表，每条记录长 `0x48`，`+0x38` 是完整武器句柄，`+0x3C` 是 definition。`+0xEDA34A` 在已经找到该武器记录时跳过创建分支；饰面热修保留句柄，因此名称缓存失效并不会让已经创建的图标自动重做 `+0xEAADCC` 的文字绑定。

本次补上最终的标签提交：

- 原生名称缓存失效后，分别回读自定义名和完整名。当前 `weapon_name_full` 消费者 `+0xE09AF1` 使用 `GetItemName(true)`，右侧标签取同一完整名，保留游戏本地化及涂装信息，不再把默认自定义标签当成涂装名称。
- 仅在配置刀具具备完整字段、材质及原生 ABI 证据后，安装 `+0xEDA090` 的 HUD 更新桥。原生更新先照常执行，随后在同一 HUD 回调内按玩家 pawn、完整武器句柄及 definition 找到现有图标。通过原生 `+0x17B8C40` 向该图标提交 `WeaponIcon--name`，不创建重复图标，不清空整个武器栏。
- 提交前重新核对物品指针、实体代次、owner、涂装、高低位 ID、配置版本及 Demo 场景代次，并要求图标 wrapper 为当前已核验的原生 Panel 类型。配置变更、seek、句柄复用、错误刀型、重复句柄和残缺表均不得使用旧请求。
- 每份配置／图标只尝试提交一次；图标重新创建后可以再次提交，原生调用失败后停止写入。原生 UI 回调之外不写标签，稳定播放不会重复生成名称或材质。
- 模型+饰面的模型和涂装继续仅由临时 Demo 重建；这条桥只处理客户端显示文字。默认手套及挂件路径不变。

验收日志现在分两阶段：`Knife HUD native name regenerated` 必须包含 `full_before`、`full_after` 和 `right_label_queued=1`；随后 `Knife right HUD label submitted` 记录实际提交的完整名称、实体句柄和 panel。仅出现第一阶段不能认定标签已经提交，两阶段均不替代最终画面验收。

新增离线回归验证精确句柄及刀型选择、同 index 不同 serial、重复或残缺记录、越界数量、指针溢出、图标重建、配置变化和十万次稳定回调不重复提交；另从真实安装 PE 验证 HUD 回调、原生标签 setter、完整名称消费者与关联调用，并逐字节破坏／截断窗口要求拒绝。测试不启动 HLAE，不调用游戏内函数。

另外将安装 PE 的 HUD 入口复制到测试进程的私有内存，只执行其空 pawn 提前返回分支，实际创建、启用并调用 MinHook 跳板，确认该入口的条件跳转可以正确重定位，且原调用的布尔参数与返回路径保留。该检查不打开游戏进程，不执行需要游戏状态的分支，也不代表游戏内标签画面已验收。
